This audit covers all three repos (`evexec`, `evexecoperator`, `evexecdriverapp`) and the shared Supabase project (`yoltkmhtxwluqxxpewbl`); the identical write-up is committed to all three repos' `CLAUDE.md`. ## Real multi-tenant foundation already exists

Migration `20260907120000_multi_tenant_foundation.sql` (applied, present in all three repos) added:

- `public.tenant_users` mapping `auth.users` → tenant + role (`super_admin` / `operator_admin` / `dispatcher` / `driver`); `tenant_id = null` reserved for platform-wide `super_admin` rows.
- RLS helper functions `private.is_super_admin()`, `private.is_member_of_tenant()`, `private.staff_for_tenant()`, used to scope staff/driver access per tenant instead of "any staff sees everything."
- `tenant_id` columns (NOT NULL, indexed, RLS-scoped) on: `bookings`, `drivers`, `missed_calls`, `quote_requests`, `contact_messages`, `reviews`, `invoices`, `profiles`. - Today there is exactly one seeded tenant (`00000000-0000-0000-0000-000000000001`, slug `ev-exec`) — the live business. The schema is real and already multi-tenant-shaped, not a greenfield redesign.
- There is also a `manage-tenants` Supabase Edge Function for tenant admin — not exercised as part of this audit, so its completeness (e.g. does it fully provision a new tenant end-to-end) is unverified.

## Cross-tenant isolation gap — 17 tables with no `tenant_id`

Confirmed via `information_schema.columns` against the live project: these tables have RLS enabled but **no `tenant_id` column at all**, so their existing policies cannot be tenant-scoped:

`notification_log`, `notification_queue`, `booking_audit_log`, `saved_addresses`, `booking_expenses`, `driver_locations`, `driver_messages`, `driver_shifts`, `job_proofs`, `booking_photos`, `notification_channel_settings`, `operator_push_subscriptions`, `push_config`, `push_subscriptions`, `driver_unavailable_dates`, `driver_events`, `audit_log`, `error_log`.

With a single tenant this is invisible — every row belongs to the one business anyway. The moment a second tenant is onboarded, any table here whose policy grants access to "any staff/driver" rather than "this tenant's staff/driver" becomes a straight cross-tenant data leak (e.g. driver locations, driver messages, or audit logs from Tenant A visible to Tenant B's staff). This is the single biggest blocker to safely running >1 tenant today and should be closed (via the same `tenant_id` + `staff_for_tenant()`/derived-join pattern the foundation migration already established) before onboarding any second operator.

## Supabase security advisor findings (live project, checked 2026-09-22)

1. **`rls_enabled_no_policy`** (INFO, 2 tables): `private.staff_users` and `public.push_config` have RLS enabled but zero policies — meaning they currently deny all access via PostgREST, which is safe but likely unintentional (something probably can't read them that should be able to).
2. **`anon_security_definer_function_executable`** (WARN, 1): `public.get_push_dispatch_bundle(p_secret text)` is callable by the fully unauthenticated `anon` role via `/rest/v1/rpc/get_push_dispatch_bundle`. Worth confirming `p_secret` is actually checked meaningfully inside the function before this ships to other tenants.
3. **`authenticated_security_definer_function_executable`** (WARN, 5): `get_push_dispatch_bundle`, `get_push_public_key`, `queue_customer_sms`, `register_operator_push`, `unregister_operator_push` are all `SECURITY DEFINER` and callable by any signed-in user, not just staff. Each should be reviewed for whether it does its own tenant/ownership check internally (elevated-privilege functions are a classic cross-tenant bypass if they don't).
4. **`auth_leaked_password_protection`** (WARN, 1): HaveIBeenPwned leaked-password checking is disabled in Supabase Auth. Free to enable, no cost — worth turning on regardless of the SaaS question.

## Update — 2026-09-22: security-advisor / live-bug fixes applied

Fixed directly against production (migration `20260922200000_fix_security_advisor_findings.sql`, present in all three repos):

- **`queue_customer_sms` abuse vector (real, live-today bug, not just a future-tenant concern)**: this `SECURITY DEFINER` function had no internal authorization check at all. `evexecoperator/src/app/api/booking-response/route.ts` calls it after only checking the caller has *some* valid Supabase session (`auth.getUser(token)`), not that they're actually staff — so any authenticated account (e.g. any customer login) could have called the RPC directly with an arbitrary `ref`/`recipient`/`body` and queued an SMS to any phone number, on the business's paid Twilio number, with attacker-controlled text. Fixed by adding an internal check that the caller is staff for the tenant that owns the referenced booking; the function now silently no-ops otherwise (matching its existing convention for invalid input).
- **`unregister_operator_push` had no ownership check** — any authenticated user who knew/guessed another user's push endpoint could unregister their device. Now scoped to `user_id = auth.uid()`. (Endpoints are long opaque browser-generated URLs, so practical exploitability was low, but the check was simply missing.)
- **`driver_locations` and `job_proofs` staff-read policies used `private.is_staff()`** (any staff of any tenant) instead of tenant-scoped access — harmless with the single current tenant, but a direct live-GPS / job-photo cross-tenant leak the moment a second tenant is onboarded. Both now scoped via `private.staff_for_tenant()` joined through the owning driver/booking, matching the pattern used elsewhere.
- **`audit_log` and `error_log` staff-read policies checked role only, with no `tenant_id` to scope by** — any staff/operator_admin/dispatcher of any tenant could have read the full platform-wide audit trail or error log (including `user_email` and stack traces) once a second tenant existed. Both tables now have a `tenant_id` column (backfilled — both were empty at fix time — and defaulted to the existing tenant; `audit_log` also gets it from the actor's own `tenant_users` row via a new insert trigger), and both read policies are now tenant-scoped.
- Verified as **not** bugs, no change made: `get_push_dispatch_bundle` (its `p_secret` param IS checked against `push_config.webhook_secret` before returning anything — the advisor's "anon-callable" WARN is a false positive against a function that's correctly secret-gated); `get_push_public_key` (returns only the VAPID *public* key, which is meant to be publicly readable by design); `register_operator_push` (already self-scoped to `auth.uid()`, no cross-user risk); `private.staff_users` / `public.push_config` RLS-enabled-no-policy (verified as default-deny — both are only ever read through the `SECURITY DEFINER` wrapper functions above, so the "no explicit policy" lint is cosmetic, not an active gap — left as-is to avoid accidentally widening access).
- The advisor will keep showing `queue_customer_sms` / `unregister_operator_push` / `register_operator_push` / `get_push_*` under "callable by authenticated/anon" — that lint only checks grants, not function bodies, so it can't see the internal checks now in place. Expected, not a residual issue.
- **Not fixed, cannot be fixed from here**: `auth_leaked_password_protection` lives in Supabase Auth config, not the Postgres schema — no tool available in this session reaches it. Toggle it yourself: Supabase Dashboard → Authentication → Sign In / Providers → Password → enable "Leaked password protection" (HaveIBeenPwned check). Free, no cost impact.
- **Re-checked every one of the other 16 gap tables' actual policies (not just their missing column) before deciding what needed fixing**: `booking_audit_log` and `driver_unavailable_dates` are already correctly tenant-scoped via a join to their owning booking/driver — no gap despite lacking their own `tenant_id`. `booking_expenses`, `booking_photos`, `driver_messages`, `driver_shifts`, `driver_events`, `push_subscriptions`, `saved_addresses` have no staff-facing policy at all — self-scoped to the owning driver/customer only, so nothing cross-tenant to leak (staff presumably reads these server-side via service role). `notification_log` and `notification_queue` are `service_role`-only, no client access at all. `push_config` has zero policies (default-deny, read only through the secret-gated function above). `operator_push_subscriptions` is self-scoped to `user_id = auth.uid()`, so a caller can only ever touch their own row regardless of tenant.

## The "two-tap automation" — standing pattern, no Twilio going forward (2026-09-23)

**Standing directive from the user: going forward, no new Twilio SMS usage, at all, for any customer- or staff-facing notification.** Email is free and stays the primary channel everywhere it already is. Push notifications (driver and operator) are free and stay as-is. Where the *only* remaining fallback today is an SMS to a human who can act on it (a driver, or "the operator"/staff), replace it with this pattern instead of Twilio:

1. Generate the message exactly as before (same templates/wording — this is a delivery-mechanism change, not a copy change).
2. Write it to a small task table (`driver_sms_reminders` for driver-targeted, `operator_sms_tasks` for staff-targeted) with `status: pending`.
3. Push-notify the recipient (the assigned driver, or every subscribed operator device) via the existing push infrastructure, deep-linking straight to a review screen for that task.
4. The recipient opens the notification (tap 1: "Open Messages" → native Messages app opens with the number and message pre-filled from the stored task), reviews it, and presses Send themselves from their own phone.
5. They return to the app and tap "Mark as Sent" (tap 2) to confirm — status only ever becomes `sent` on that explicit confirmation, never assumed.

Hence "two-tap": one tap opens Messages pre-filled, one tap confirms it was sent. No Twilio API call happens anywhere in this flow — the SMS goes out over the human's own phone/mobile plan.

**Implemented so far:**
- **Driver reminder SMS** (customer 7-day/24-hour reminder, when the customer has no email on file) → `driver_sms_reminders` table, `send-customer-sms-reminder-push` edge function (evexecdriverapp), reminder screen at `evexecdriverapp` `/jobs/[id]/reminder`.
- **Booking confirmation SMS** and **rejection ("journey unavailable") SMS** to the customer (both email-primary, only reached when there's no email on file) → `operator_sms_tasks` table, `evexecoperator`'s `/api/push/notify-operators` route, review screen at `evexecoperator` `/operator/sms-tasks/[id]`. Wired from `evexec/lib/notify.js`'s `handOffSmsToOperator()`. The redundant Twilio SMS-to-operator's-own-phone fallback in the same function (`sendConfirmations`) was removed outright rather than converted — operator push + email already cover that case, so there was nothing customer-facing left needing the two-tap review step there.

**Remaining Twilio SMS call sites — not yet converted, flagged for follow-up:**
- `evexec/api/operator/index.js` — operator-accepted notice to the customer (email-primary, SMS fallback), and a manual "send SMS" action available to staff from the dashboard.
- `evexecoperator` — operator status-update SMS to the customer (migrations `008_operator_status_update_sms.sql` / `020_customer_pings_enroute_arrived_only.sql` and friends) and the `send-sms` edge function it's built on.
- `evexecdriverapp/supabase/functions/notify-passenger-arrived` and `send-journey-receipt` — driver-triggered arrival/receipt SMS to the customer, via `_shared/twilio.ts`.
- `evexec/api/notifications/index.js`'s health-check test send (`handleHealth`) — an admin diagnostic button, not a customer/staff notification; lower priority since it isn't part of any automated flow and only fires when an admin explicitly tests the Twilio config.

Each of these fits the same shape (email/push primary, Twilio-SMS-only-as-fallback) and can be converted the same way — write a task row, push the right human, let them send it themselves. Ask before starting the next one, since each touches a different flow and is worth confirming scope on individually rather than converting all of them in one pass.

### Update — 2026-09-23: reminder duplicate eliminated, 'received' converted, payment links converted (closes out the two-tap sweep)

Follow-up to the same-day investigation above (the one that flagged `received`/`reminder_24h` as needing a "who wins" check before converting). Confirmed and fixed all three:

- **`reminder_24h` was a genuine live duplicate** for operator-sourced bookings: `enqueue_operator_customer_notifications()` queued its own `reminder_24h` row on `INSERT`, completely independently of `evexec`'s own `/api/reminders/trigger.js` cron, which queues the same reminder type for every booking regardless of `source`. The two systems couldn't see each other's sends because `notificationQueue.js`'s `markSent()` never writes to `notification_log` — the exact table `alreadyReminded()` checks for dedup — so there was no cross-system signal stopping the second send. Fixed by deleting the `reminder_24h`-creation block from the trigger entirely: `evexec`'s cron is now the single owner of both `7day` and `24hr` reminders for every booking, operator-sourced or not. 8 already-queued, still-pending Twilio SMS rows created by the trigger before this fix were deleted directly (verified 0 remain). To avoid losing content for operator-sourced bookings (the trigger's own reminder included driver name/vehicle/registration when assigned), `evexec/api/reminders/trigger.js` was enriched to fetch and include the same driver details, so the single remaining reminder path doesn't regress in quality.
- **`received` (booking confirmation) does NOT collide** with `evexec`'s own `sendConfirmations()` — confirmed via Stripe metadata keys: `evexec`'s own checkout session sets `metadata[bookingId]` (read by its own webhook handler); `evexecoperator`'s separate `payment-link` route sets a different key, `metadata[booking_ref]`, so the two systems' webhooks never fire for the same session. With collision ruled out, the trigger's `received` SMS branch was converted to two-tap the same way as everywhere else — hands off to staff via `operator_sms_tasks` (`kind: 'confirmation'`, reusing the same kind `evexec`'s own confirmation flow already uses), with an existence check against both systems' tables so a booking can't get double-queued.
- **`evexecoperator`'s payment-link route** (`/api/payment-link`) was the third, previously-unflagged live Twilio site: it unconditionally texted the Stripe checkout link via `notification_queue` regardless of whether the customer had an email on file. Converted to email-primary — sends a branded HTML email via Resend (same template conventions as `send-invoice`) when `customer_email` is present, synchronously, in the same request — and when there's no email, returns an `sms:` two-tap deep link in the API response for the operator's own dispatch screen to open directly (`window.location.href`), rather than queuing anything for Twilio. No push-notify-self step needed here since sending the link is already an explicit, synchronous action the operator just took.

Migration: `20260923143619_consolidate_reminders_and_convert_received_sms.sql`.

**Twilio SMS call sites — remaining, not yet converted:**
- `evexec/api/operator/index.js` — operator-accepted notice to the customer (email-primary, SMS fallback), and a manual "send SMS" action available to staff from the dashboard.
- `evexecdriverapp/supabase/functions/notify-passenger-arrived` and `send-journey-receipt` — driver-triggered arrival/receipt SMS to the customer, via `_shared/twilio.ts`.
- `evexec/api/notifications/index.js`'s health-check test send (`handleHealth`) — an admin diagnostic button, not a customer/staff notification; lower priority since it isn't part of any automated flow.

### Update — 2026-09-24: root-caused and fixed a real off-by-one-day bug in customer reminder emails

A customer reported receiving a reminder email that said "your transfer is tomorrow" but showed today's date inside it — genuinely confusing, and a real live bug, not a one-off. Audited every date-formatting call site across all three repos rather than guessing.

**Root cause found in `evexec/lib/format.js`'s `fmtDate()`** (used by the reminder cron for every email/SMS/push it sends, plus the customer's own booking status page in `booking.html`, which had an identical duplicate copy of the same function): `travel_date`/`return_date` are stored as plain `YYYY-MM-DD` strings with no time component. `new Date(dateStr)` parses that as **UTC midnight**. `fmtDate()` then called `.toLocaleDateString('en-GB', {...})` with **no explicit `timeZone`**, so the displayed date silently used whatever timezone the Vercel serverless process happened to be running in — on any host west of UTC, that rolls the displayed date back one calendar day. A booking stored as the 25th could display as the 24th, while the reminder's separate "tomorrow" wording (computed correctly via a proper BST/GMT-aware conversion in `travelDateTimeUtc()`) stayed right — exactly the "says tomorrow, shows today" mismatch reported. Reproduced directly (`new Date('2026-09-25')` formatted with `timeZone: 'America/New_York'` prints "24 September 2026").

Fixed by always formatting in UTC (`timeZone: 'UTC'`), which recovers the exact stored calendar date regardless of server locale, in every vulnerable call site found:
- `evexec/lib/format.js` — `fmtDate()`, feeding every customer reminder email/SMS/push.
- `evexec/booking.html` — its own duplicate `fmtDate()`, the customer's own booking status page.
- `evexecoperator/src/components/BookingCard.tsx` — `displayDate()`, shown on dispatch/calendar cards for both travel and return dates.
- `evexecoperator/src/components/operator/BookingDetailDrawer.jsx` — the return-date row.

**Audited and confirmed safe** (same-looking `toLocaleDateString`/`toLocaleString` calls that are *not* the same bug, so left untouched): anywhere a date-only string is parsed via `new Date(\`${d}T00:00:00\`)` (no `Z` suffix) or `new Date(year, month-1, day)` — both parse as *local* time, and are then rendered without a timezone override too, so the two sides stay consistent regardless of server locale (`evexecoperator`'s `invoices/page.jsx` `longDate()`, `dispatch/page.jsx`'s day bucketing, `evexecdriverapp`'s shared `lib/format.ts` `formatDate()` used by both the driver reminder screen and elsewhere). Anywhere formatting an actual timestamp (`created_at`, `sent_at`, `completed_at`, etc.) rather than a date-only field is a much lower-severity version of the same class (only shifts near a midnight boundary, not always) and wasn't touched in this pass — flagged if it becomes worth a dedicated sweep. `evexecdriverapp`'s own reminder/notification edge functions (`send-driver-reminders`, `notify-job-update`) already specify `timeZone: 'Europe/London'` explicitly — correctly built from the start.
